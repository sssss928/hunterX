# HunterX v0.4.8 operations guide

## Absolute sale time

Enter an exact value such as `2026/08/10 11:00:00.000`. HunterX interprets the
runtime target in `Asia/Taipei` (UTC+08:00), preserves all three millisecond
digits, and maps it to a monotonic one-shot deadline. It does not silently
refresh early. If you intentionally want an earlier target, enter that time
yourself.

Before a sale on Windows:

1. Open **Settings → Time & language → Date & time**.
2. Enable automatic time and timezone, confirm the timezone is Taipei, then
   select **Sync now**.
3. Optionally run `w32tm /query /status` in PowerShell and verify the service
   reports a recent successful synchronization.
4. Do not change the system clock inside the final ten-second arm window.

HunterX can report a clock jump but cannot repair an incorrect OS clock,
network latency or server-side opening time.

## On-sale preflight

Use `onsale` for a known sale boundary. Start early enough to verify:

- the intended event/activity page is open and not an order/checkout page;
- the correct account is visibly signed in, or the site clearly requires a
  later manual sign-in/challenge;
- ticket count, date keywords, area keywords, exclusions and fallback switches;
- `allow_less_tickets` is off unless fewer tickets are genuinely acceptable;
- CAPTCHA/qualification/member-code settings and manual handoff expectations;
- Chrome remains connected and no Queue-it/Cloudflare waiting room is active;
- the target time and Windows clock are correct.

At the deadline HunterX requests one guarded reload and immediately continues
through the same platform purchase handlers. A platform-owned countdown or
waiting room remains authoritative where the capability matrix says manual
reload is unsafe.

## Leak-watch operation

Use `leak_watch` for sporadic releases or cleared inventory. The configured
`leak_refresh_interval_seconds` is the deterministic minimum interval on safe
pages. Start with at least three seconds unless the platform's published
behavior calls for a longer interval. Faster is not automatically better and
can increase throttling or soft blocks.

After a reload, HunterX scans the new document. A completed no-ticket result is
not repeatedly rescanned in the hot loop; it waits for the next deadline. If a
ticket appears, pending refresh work is canceled by the purchase-page guard and
the normal purchase flow takes over. Queue, challenge, ticket, order, checkout
and payment routes never become leak-refresh targets.

## Reading refresh and soft-block logs

Enable verbose diagnostics when troubleshooting. Relevant records include:

- `[REFRESH] dispatch`: reason, priority, generation, monotonic start and
  scheduled lateness;
- `[REFRESH] suppressed`: minimum interval, coalesced schedule, soft-block wait,
  in-flight action or purchase guard;
- `[EPS BLOCK]`: `SUSPECTED`, `CONFIRMED_WAIT`, `RECOVERING` and recovery result;
- `[AREA] dom_read_skipped reason=generation_already_scanned`: leak-watch is
  waiting normally, not stuck;
- `[URL DIAG] safe_stop`: the browser/CDP connection returned no URL for 30
  seconds and HunterX stopped without navigating.

The configured soft-block delay applies to TixCraft/TeamEar/Indievox scope.
Leaving it empty resolves one safe 240–420 second value per incident. Repeated
observations and hot-reloaded settings do not shorten an active incident. If a
safe stop or persistent browser disconnect occurs, inspect the visible browser,
close only the affected HunterX instance, and restart it manually; automatic
reconnection could discard an in-progress order.

## Manual validation before an important event

Use a non-purchasing test page or stop before submission:

1. Confirm the packaged `settings.exe` opens from a directory containing spaces.
2. Save and reload the intended profile; verify the displayed mode and time.
3. Open the target public event page and confirm login/session and route
   classification messages.
4. Verify manual tabs remain open when the bot creates/closes its own popup.
5. Practice the CAPTCHA, qualification and checkout handoff without completing
   a real purchase.

Offline fixtures cannot certify a changed live DOM or guarantee tickets. Never
publish logs containing cookies, tokens, account data or payment information.
