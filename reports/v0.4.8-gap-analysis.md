# HunterX v0.4.8 gap and upstream analysis

Baseline: official HunterX v0.4.7 tag at
`15298d72aea6d42e6b4d954e8fd1e426d01a67f9`. Upstream comparison:
`bouob/tickets_hunter` v2026.08.07 at
`5793ee6daba562c42c902a1b84625528e421f849`, including integration commit
`96c1c14ec13c1149d7ae60dfc94e9ebdb37142b4`. No merge, commit, tag or push was
performed.

## Root-cause and acceptance map

| Symptom | Reproduction / code evidence | Root cause | v0.4.8 design | Risk and acceptance evidence |
|---|---|---|---|---|
| Soft block eventually refreshes each second | Repeat inconclusive recovery for hours | `_defer_tixcraft_soft_block_recovery` assigned `current + 1.0` after failed/inconclusive recovery | Immutable incident wait/deadline, explicit state, ordinary-intent suppression, one recovery | 10 virtual hours / 360,000 loop ticks; retry gaps remain at least configured seven seconds; focused soft-block suite |
| Exact target reload is late | Arm a millisecond target while the health watchdog is due | Near-boundary watchdog used interval zero and could start CDP/DOM work before dispatch; Windows one-millisecond sleeps were unreliable | Frozen aware wall→monotonic deadline, no new boundary probe after target, cooperative final yield, scheduled one-shot | Fake-clock wall jumps/stalls, millisecond and timezone tests; 1,000 controlled dispatches p95 ≤50 ms and max ≤100 ms |
| Interval looks random | Trigger reloads from several platform handlers, including calls without config | Platform loops owned local deadlines; common guard could see interval zero; no common per-tab dispatch clock | One coordinator per tab plus PlatformEngine atomic config snapshot; `next_allowed = actual_start + interval`; no catch-up | 50,000 ticks, stall test, repeated legacy-call integration, deterministic bounded trace |
| Modes feel identical | Compare `onsale` and `leak_watch` on unchanged no-ticket DOM | Modes used different intervals but leak-watch could still rescan the same document in the hot loop | Shared purchase handlers; separate scheduling policy; one completed no-ticket scan per document generation | Mode interval tests, generation transition tests, pending-state liveness tests |
| Ticketmaster wrong quantity/detail behavior | Target 4 with options 1/2/5; open `/activity/detail/` | Fallback selected maximum option even above target; TixCraft redirect claimed Ticketmaster detail | Exact default, largest strictly smaller only when enabled; Ticketmaster date handler claims detail | Synthetic exact/less/never-more cases and route tests |
| KKTIX qualification races | Qualification radio inserts/enables a member field after ticket selection | Document-wide duplicated form logic could fill/submit before the selected unit was ready | One scoped state read; select qualification, wait, fill, recheck, next | Ordered synthetic DOM integration and invitation/manual fail-closed test |
| Manual tabs can close | Open a user tab before Ticketmaster/Cityline bot popup | Extra-tab logic inferred ownership from tab count | Bounded ownership registry; close only newly observed bot-owned tabs | Owned/unowned and pre-existing Cityline fixture tests |
| Long empty URL spins forever | Return empty cached/CDP URL continuously | Main loop logged and continued without a terminal policy | Rate-limited diagnostics and safe stop after 30 seconds; manual restart | Source-path regression plus connection classifier tests; live disconnect remains manual validation |
| Dead overheat keys conflict with interval meaning | Load an older profile containing both keys | Unused legacy state remained in defaults/migration vocabulary | Remove/deprecated-ignore during migration; never maps to one-second pacing | Migration test preserves interval and user exclusions |

## Baseline evidence

- Python 3.11.9; pytest 9.1.1; Ruff 0.15.20; mypy 1.20.2.
- 646 baseline tests collected. The monolithic baseline run exceeded the
  available 300-second command window; this is recorded as incomplete, not a
  pass or failure.
- Baseline compileall, Ruff, configured mypy, pip-audit and high-severity Bandit
  checks passed. The benchmark plugin executed six cases then failed in the
  host `py-cpuinfo` probe, so a portable benchmark runner was used for before /
  after comparison.
- Baseline portable timings are preserved in the validation report. No live
  ticket, CAPTCHA, queue or payment action was used as evidence.

## Remaining risk

Synthetic fixtures prove local invariants, not current live-site selectors or
inventory. Browser/network/server latency can exceed controlled dispatch
limits. System clock correctness remains the user's responsibility. All
purchase, challenge and payment transitions require the manual checklist in
`guide/v0.4.8-operations.md` before a high-stakes event.
